# 01 需求分析

這一章記錄 HomeVault 要解決什麼問題。需求的來源標記如下：

- 📄 **依據**：有明確來源。主要來源是本次開發對話中使用者提供的題目「家用增量備份工具（HomeVault）」，以下簡稱「題目」。
- 🔍 **推斷**：從程式碼或情境推論而來，請自行確認。

## 1. 背景與目標

> 📄 依據：題目「案名與客戶背景」

一個五口之家有兩台電腦：一台 Windows、一台 Mac。十幾年的照片、影片和報稅資料，平常只是偶爾把整個資料夾複製到外接硬碟。硬碟裡已經有十幾份重複的副本，空間快滿了。

他們要的是一個能**自動增量備份、節省空間、加密**的工具，並且：

- 每晚 11 點自動執行，而那個時間家裡**常常還有人在用電腦**；
- 家人常在**備份跑到一半時直接拔走外接硬碟**。

這兩句話是整個設計的關鍵。前者帶出「低優先權執行」與「檔案可能正被使用」，後者帶出整套中斷安全設計（見 [11 章](11-tradeoffs-pitfalls.md)）。

## 2. 使用者與角色

| 角色 | 說明 | 來源 |
|---|---|---|
| 家庭成員 | 共用同一組密碼，不需要多使用者權限 | 📄 題目「假設事項」 |
| 作業系統排程器 | cron、launchd 或 Windows 工作排程器，每晚觸發 `homevault backup` | 📄 題目「排程由作業系統的工作排程器或 cron 負責」 |
| 另一台電腦 | 同一個備份庫由 Windows 與 Mac 共用；「同一時間只有一台電腦執行指令，但可以預期有人忘記這件事」 | 📄 題目「假設事項」 |

## 3. 功能需求

### 切塊、去重與加密

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-01 | 以內容定義切塊（CDC）切檔，平均 1 MiB、最小 256 KiB、最大 4 MiB，演算法必須自行實作 | 📄 題目 |
| FR-02 | 相同內容的區塊只存一份，跨檔案、跨快照、跨兩台電腦都要去重 | 📄 題目 |
| FR-03 | 區塊壓縮後打包成約 16 MiB 的 pack 檔，避免在外接硬碟上產生數十萬個小檔案 | 📄 題目 |
| FR-04 | 以 scrypt 或 Argon2 從密碼推導金鑰，所有區塊與中繼資料都以 AES-GCM 加密 | 📄 題目 |
| FR-05 | 區塊識別碼以 HMAC-SHA256 計算，不可直接使用內容的 SHA-256 | 📄 題目 |
| FR-06 | 密碼錯誤時清楚提示，不可損壞任何資料 | 📄 題目 |

### 快照、還原與瀏覽

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-07 | `backup` 建立快照，記錄路徑、大小、修改時間、權限、區塊清單與主機名稱 | 📄 題目 |
| FR-08 | 大小與修改時間都和上一個快照相同時，沿用區塊清單、不重新讀取；提供 `--full-scan` | 📄 題目 |
| FR-09 | 可設定排除規則（`*.tmp`、`node_modules`、`.DS_Store`） | 📄 題目 |
| FR-10 | 可還原整個快照、單一資料夾或單一檔案到指定位置 | 📄 題目 |
| FR-11 | 還原時逐區塊驗證完整性，並還原修改時間 | 📄 題目 |
| FR-12 | 列出快照、瀏覽快照內的目錄、比較兩個快照的差異 | 📄 題目 |

### 保留政策、清理與完整性

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-13 | `forget` 依保留政策刪除舊快照（例如 7 天、4 週、12 個月） | 📄 題目 |
| FR-14 | `prune` 移除沒有被引用的區塊；pack 只有部分區塊仍在使用時，重新打包 | 📄 題目 |
| FR-15 | `check` 驗證 pack 與索引的一致性；`--read-data` 解密並驗證每個區塊 | 📄 題目 |
| FR-16 | 發現損毀時，列出受影響的快照與檔案 | 📄 題目 |
| FR-17 | `stats` 顯示總大小、原始資料總量、各快照的獨有資料量 | 📄 題目 |
| FR-18 | 備份時顯示速度、已處理量、新增資料量與去重比例 | 📄 題目 |

### 中斷安全

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-19 | backup、forget、prune 在任何步驟中斷（Ctrl+C、拔硬碟、斷電），備份庫都不可損毀，原有快照都能完整還原 | 📄 題目 |
| FR-20 | 備份中斷後重跑，已寫入的區塊要能重複使用 | 📄 題目 |

### 開發過程中新增的需求

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-21 | 被鎖住或讀不到的檔案、資料夾不可從快照中消失：沿用上一個版本並標記「自某日起無法更新」 | 📄 開發後期使用者貼上的審查回饋（commit `e876344`） |
| FR-22 | 備份途中被修改的檔案要重讀；仍在變動就標記並反映在 exit code | 📄 同上 |
| FR-23 | 執行期間若 lock 被另一台電腦判定為殘留而移除，必須在提交快照或刪除資料前察覺並中止 | 📄 本次開發中的獨立程式碼審查（commit `3097131`） |

## 4. 非功能需求

| 編號 | 需求 | 來源 |
|---|---|---|
| NFR-01 | Python 3.12 以上，CLI 介面 | 📄 題目 |
| NFR-02 | 在 Windows 與 macOS 上執行；備份庫放在 exFAT 外接硬碟，兩台電腦共用 | 📄 題目 |
| NFR-03 | 不需要資料庫、不需要 Docker | 📄 題目 |
| NFR-04 | 首次備份 500 MiB 混合資料在 60 秒內完成 | 📄 題目驗收 12 |
| NFR-05 | 規模上限：2 TB、200 萬個檔案 | 📄 題目「假設事項」 |
| NFR-06 | 備份庫的檔名與中繼資料不洩漏原始檔名或內容雜湊 | 📄 題目驗收 6 |
| NFR-07 | 晚上 11 點執行時不拖慢家人正在使用的電腦 | 🔍 推斷：由背景「那個時間家裡常常還有人在用電腦」推導，設計討論時列為隱含需求（見 `docs/design.md` §1.1） |
| NFR-08 | 排程執行時沒有終端機，必須能以非互動方式提供密碼 | 🔍 推斷：同上，由「每晚自動執行」推導 |
| NFR-09 | 測試至少 45 個並全數通過，建議使用 Hypothesis | 📄 題目驗收 13 |

**品質屬性的優先順序**（衝突時依此取捨）：資料不可損毀 > 隱私 > 空間效率 > 效能 > 易用性。

> 📄 依據：`docs/design.md` §1.2，於開發前的設計討論中提出並經使用者確認

## 5. 範圍外

> 📄 依據：題目「假設事項」

- 雲端備份（只支援本機路徑：外接硬碟或網路磁碟）
- 多使用者權限
- 系統檔案、ACL、延伸屬性、資源分支
- 跟隨符號連結（只記錄連結本身）
- 圖形介面、內建排程器

## 6. 未解決或待確認的需求問題

| 問題 | 目前做法 | 狀態 |
|---|---|---|
| 題目說「pack 只有部分區塊仍在使用時，重新打包」，但每個 pack 都重寫並不划算 | 未使用比例超過 20% 才重新打包，可用 `--repack-threshold 0` 改成全部重寫 | 已在報告中提出，使用者尚未表示要改 |
| 「保留最近 7 天每天一份」的語意 | 採「有快照的最近 7 個日子」（restic 的語意） | 📄 使用者已確認 |
| Windows 上刪除檔案無法保證斷電後持久化 | 列為已知限制 | 未處理 |
| macOS 主機名稱可能隨網路變動，導致失去增量判斷 | 可用 `--host` 固定 | 未處理 |
| 更改密碼 | 格式已支援（key file 與 master key 分離），沒有指令 | 未處理 |
