# 11 設計取捨與踩坑紀錄

## 第一部分：設計取捨

### ADR-1：用 numpy 向量化切塊

- **決策：** 切塊的主要實作用 numpy 向量化，純 Python 版本只保留給測試對照。
- **考慮過的選項：** 純 Python、C 擴充、multiprocessing、numpy。
- **選擇與理由：** 📄 開發前實測，純 Python 只有 15 MiB/s，numpy 版 173 MiB/s。設計討論時提出，使用者確認採用。
- **代價：** 多一個約 20 MB 的相依套件，而且演算法的寫法比逐 byte 迴圈難懂。為此保留了參考實作，並以 Hypothesis 證明兩者等價。

### ADR-2：快照採用 Merkle 樹，而不是單一大清單

- **決策：** 每個目錄一個 tree blob，id 由內容決定。
- **考慮過的選項：** 每個快照一份完整的檔案清單。
- **選擇與理由：** 📄 `docs/design.md` §4.5。200 萬個檔案的清單約 300 MB，每晚存一份不可行；Merkle 樹讓沒有變動的目錄自動去重。
- **代價：** 讀取一個檔案要先一層層載入 tree，而且單一目錄有大量檔案時，對應的 tree blob 會很大。

### ADR-3：pack header 放檔尾、檔名是密文的 SHA-256

- **決策：** 寫法參考 restic：header 放在檔尾，檔名是內容的雜湊。
- **選擇與理由：** 📄 `docs/design.md` §4.1、§4.3。header 放檔尾，可以邊寫邊串流，pack 也能自我描述（中斷復原的基礎）。雜湊的對象是密文，所以不洩漏內容；檔名同時也是校驗碼。
- **代價：** 讀 header 需要兩次讀取（先讀長度，再讀 header）。

### ADR-4：保留政策採用「有快照的日子」

- **決策：** 「最近 7 天每天一份」指的是「有快照的最近 7 個日子」。
- **考慮過的選項：** 從今天往回數 7 個日曆天。
- **選擇與理由：** 📄 設計討論時提出、使用者確認。電腦關機兩週後再開機，舊的每日快照不會一次被刪光。
- **代價：** 長期沒有備份時，保留下來的「每日」快照可能橫跨好幾週，與字面意思不同。

### ADR-5：保留政策依「主機＋來源路徑」分組

- **選擇與理由：** 📄 使用者確認。Windows 與 Mac 各自保留自己的 7 天、4 週、12 個月。
- **代價：** 主機名稱改變（macOS 偶爾會發生）時，會被當成另一組，見 [01 章](01-requirements.md) 待確認事項。

### ADR-6：backup 用共享鎖，forget 與 prune 用獨佔鎖

- **選擇與理由：** 📄 `docs/design.md` §5.5。backup 只會新增檔案，所以兩個 backup 同時執行是安全的；只有刪除才需要獨佔。
- **代價：** 長時間的備份期間，另一台電腦無法執行 prune。

### ADR-7：prune 重新打包的門檻預設 20%

- **選擇與理由：** 🔍 這是開發中我自己做的決定。題目原文是「部分區塊仍在使用時重新打包」，但每個 pack 都重寫並不划算。已在報告中向使用者說明，使用者尚未表示意見。
- **代價：** 與題目的字面要求不同；可用 `--repack-threshold 0` 改成完全照字面要求。

### ADR-8：讀不到的檔案沿用舊版本，而不是略過

- **選擇與理由：** 📄 使用者貼上的審查回饋（見下方踩坑紀錄第 12 項）。
- **代價：** 快照中的檔案可能不是當晚的版本。為此以 `stale_since` 明確標記，並以 exit code 3 讓使用者知道。

### ADR-9：故障注入窮舉每一個操作，而不是抽樣

- **選擇與理由：** 📄 開發中的決策。題目要求至少 20 個中斷點；從範本複製出完全相同的狀態後，窮舉的成本只有約 40 秒，卻能涵蓋約 89 個中斷點。
- **代價：** 前提是操作序列必須是確定的。這個前提後來被明確地加上檢查（`sequence_mismatch()`，見第 15 項）。

## 第二部分：踩坑紀錄

依發現順序排列。每一項都對應實際的 commit。

### 1. 硬碟被拔除後，在內建硬碟上重建備份庫目錄

- **症狀：** `test_unplugged_drive_is_reported_as_unavailable` 失敗：預期拋出「無法存取」，實際上卻寫入成功。
- **原因：** `_op_write` 用 `path.parent.mkdir(parents=True)`，會把整條路徑（包括已經不存在的備份庫根目錄）重新建立。在 macOS 上，硬碟被拔除後 `/Volumes/Backup` 會消失，這時程式會在**內建硬碟上**建立同名目錄，然後繼續把備份寫進去。
- **解法：** `_ensure_parent()` 在建立任何目錄前，先確認根目錄存在（commit `4954954`）。
- **教訓：** `mkdir(parents=True)` 不適合用在「某個上層目錄必須已經存在」的情境。

### 2. 同一個 `Repository` 物件的統計數字會累積

- **症狀：** 跨主機去重測試中，第二次備份的「新增資料量」等於第一次加第二次的總和。
- **原因：** `repo.stats` 是累計值，而測試中同一個物件執行了兩次備份。CLI 每次都重新開啟備份庫，所以平常看不出來。
- **解法：** `run_backup()` 改為記錄起點，並以差值計算（commit `2bd941b`）。

### 3. prune 在沒有東西可清時，仍然重寫 index

- **症狀：** 「prune 兩次，第二次不應該有任何變化」的測試失敗：備份庫大小從 148518 bytes 變成 148404 bytes。
- **原因：** 每次 prune 都會重寫並合併 index。
- **解法：** 沒有要刪除或重新打包的 pack 時，直接返回（commit `7ac1563`）。
- **教訓：** 每一次不必要的寫入，都會多一個中斷點。

### 4. 空的備份庫上，forget 沒有規則也不報錯

- **原因：** 驗證寫在 `apply_policy()` 裡，但空的備份庫沒有任何分組，這個函式根本沒有被呼叫。
- **解法：** 改在 `run_forget()` 的入口驗證（commit `7ac1563`）。
- **教訓：** 參數驗證要放在入口，不要放在「可能不會被執行到」的深處。

### 5. lock 的 refresh 執行緒與 release 競爭

- **原因：** `release()` 刪除 lock 的同時，refresh 執行緒可能剛好寫出一個新的 lock 檔，造成新寫出的 lock 被遺留下來。
- **解法：** `release()` 先 join refresh 執行緒，再刪除 lock 檔（commit `07c0886`）。

### 6. 取得 lock 失敗時，session 沒有失效

- **原因：** `acquire()` 只在 `RepositoryLockedError` 時清理。如果是其他例外（當機、Ctrl+C），session 會一直留在 `_active_sessions` 裡，之後同一個行程會誤以為那個殘留的 lock 還在使用中。
- **解法：** 改為 `except BaseException`（commit `061e829`）。這是撰寫故障注入測試時，閱讀程式碼發現的。

### 7. lock 被另一台電腦移除，卻沒有察覺

- **症狀：** 獨立程式碼審查提出的情境：Mac 睡眠超過 30 分鐘 → Windows 的 prune 判定 Mac 的 lock 為殘留並刪除 → prune 刪掉 Mac 已寫入、但還沒被快照引用的 pack → Mac 醒來後提交了一個引用不存在資料的快照。
- **原因：** refresh 執行緒第一次失敗就靜默結束；而且提交快照之前，沒有人確認 lock 是否仍然有效。
- **解法：** 新增 `Lock.check_held()`：太久沒有更新就先補更新，補更新時發現舊 lock 已經被刪除，就判定失效並中止。另外，refresh 失敗時改為重試（commit `3097131`）。
- **教訓：** 故障注入只模擬「單一行程當機」；「兩台電腦加上長時間停頓」屬於並行問題，是另一種故障模型。外部審查的價值在於看見模型本身的盲點。

### 8. `os.walk` 會吞掉讀取錯誤

- **原因：** `os.walk` 預設會忽略 `scandir` 的錯誤，並回傳不完整的結果。如果 prune 時讀到不完整的快照清單，就會把其他快照仍在使用的資料刪掉。
- **解法：** `os.walk(base, onerror=_raise)`（commit `3097131`）。
- **教訓：** 標準函式庫中「預設安靜」的 API，要特別留意。

### 9. Windows：fsync 需要可寫入的 handle

- **原因：** Windows 的 `os.fsync` 底層呼叫 `FlushFileBuffers`，用唯讀模式開啟的檔案會失敗。
- **解法：** `_op_fsync` 改用 `O_RDWR` 開檔（commit `ef75fe6`）。這是在本機（macOS）上閱讀程式碼時發現的，同一個 commit 也修正了還原路徑中的 Windows 磁碟代號。

### 10. Windows：輸出被導向時遇到中文就當掉

- **症狀：** CI 的 `cross-os-second` 失敗：`UnicodeEncodeError: 'charmap' codec can't encode characters`。
- **原因：** Windows 上，輸出被導向檔案或 pipe 時，Python 會改用 ANSI 編碼（英文版為 cp1252，繁體中文版為 cp950）。README 建議的「排程並寫入 log」在 Windows 上會直接失敗。
- **解法：** `ensure_utf8_output()`，並用 `PYTHONIOENCODING=cp1252` 的子行程測試在 macOS 上重現（commit `5938516`）。
- **教訓：** 在 macOS 上永遠不會出現的問題，跨平台 CI 才抓得到；逐行閱讀程式碼也沒有發現這個問題。

### 11. 測試的門檻值依賴平台

- **症狀：** Windows 上 `test_full_scan_rereads_every_file` 失敗（`2134 < 2000`）。
- **原因：** 斷言「新增資料 < 2000 bytes」也把目錄中繼資料算了進去。Windows 的暫存目錄層級很深，而且 mtime 一直在變，所以會多寫幾個 tree blob。
- **解法：** 改為直接斷言「新增的 blob 全部是 TREE，沒有任何 DATA」（commit `902c73f`）。
- **教訓：** 測試應該斷言「意圖」，而不是某個剛好成立的數字。

### 12. 每晚都被鎖住的檔案會從快照中消失

- **症狀：** 使用者貼上的審查回饋：第 0 晚 `mail.pst` 正常備份，之後每晚都被鎖住，第 1、2、3 晚的快照中都沒有它。
- **原因：** `_store_file` 遇到 `OSError` 就回傳 `None`，節點被丟掉。讀不到的資料夾也會變成空資料夾。
- **後果：** 保留政策跑久了，含有舊版本的快照被 forget 之後，這個檔案就完全沒有備份了。
- **解法：** 沿用上一版並標記 `stale_since`；同時處理備份途中被修改的檔案（重讀，並標記 `changing`）（commit `e876344`）。
- **教訓：** 「略過並記錄警告」在備份工具中並不安全，因為警告沒有人會看，但快照會一直被使用。

### 13. NTFS 的 mtime 精度只有 100 奈秒

- **症狀：** 新的「被鎖住三晚」測試在 Windows 上失敗。
- **原因：** 測試讓每晚的 mtime 只差 1 奈秒，被 NTFS 截掉；而且每晚的內容長度剛好相同，增量判斷認定檔案沒有變動，根本沒有開檔。
- **解法：** 測試中的 mtime 改以秒遞增（commit `51d46d8`）。

### 14. 依賴固定等待時間的測試不穩定

- **症狀：** Windows CI 上 `test_lock_refresh_updates_timestamp` 偶爾失敗。
- **原因：** 固定 `sleep(0.3)`，但 CI 機器寫檔加上 fsync 可能超過這個時間。
- **解法：** 改為最多輪詢 5 秒（commit `3d98ee3`）。

### 15. 測試失敗被管線吞掉，而且無法重現

- **症狀：** 本機一次完整執行出現「7 failed、25 skipped」（正常是 31 skipped），但 `uv run pytest -q | tail -1 && git commit && git push` 中的 `tail -1` 讓失敗沒有中止 commit 與 push，失敗訊息也沒有保存。
- **調查：** 三個假設都排除了：重跑 14 次、多執行緒在高負載下的 pack 配置、40 把不同的金鑰。原因至今不明。
- **解法：**
  - 流程上改用 `set -o pipefail`，並保存完整輸出；
  - 測試中加入操作序列一致性的診斷（`sequence_mismatch()`）（commit `7495d8f`）。
- **教訓：** 沒有保存的失敗訊息無法事後分析；失敗之後也絕對不能繼續 commit。

## 第三部分：潛在風險

以下是 🔍 推斷，尚未發生：

- **時鐘：** lock 的殘留判定依賴兩台電腦的時鐘，兩台時間差距很大時可能誤判。
- **Windows 上刪除檔案的持久性：** forget 之後如果立刻斷電，被刪除的快照可能「復活」；如果它引用的資料已經被 prune，之後的 prune 會中止。
- **記憶體：** 2 TB 時索引約需 300 MB；資料量再大就會成為瓶頸。
